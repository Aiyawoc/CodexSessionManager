## 1. 正式决策

2.4 按以下结论关闭：

> **停止推进当前的“上下文应用执行层”，保留并完善“上下文审查与投影计划层”；将 2.4 以“上游能力阻塞、源任务保持完整”的结果正式关闭。**

本结论不是把一次失败包装成成功，也不是放弃上下文管理目标。它确认了以下事实：

1. CSM 已能读取、审查、投影并密封上下文计划；
2. CSM 已正确复核源任务指纹，并在执行失败后保持源任务不变；
3. 当前本机 Codex CLI `0.142.1` 的 `thread/inject_items` 返回值不能证明注入内容已经持久化、可读取或可供后续模型使用；
4. 公开 App Server 目前没有经过本机验证的“把自定义 replacement history 安装回原任务”接口；
5. 因此，CSM 不得把空派生任务、请求已接受或未验证的压缩结果标记为上下文裁剪成功。

## 3. 标准化判定

2.4 的最终机器可读判定应使用以下语义：

```json
{
  "phase": "2.4",
  "status": "closed_with_upstream_blocker",
  "title_rename_restore": "passed",
  "memory_edit_restore": "passed",
  "context_projection_planning": "passed",
  "source_preservation": "passed",
  "derived_thread_roundtrip": "failed",
  "context_projection_application": "blocked_upstream",
  "production_context_trimming": "unavailable",
  "permanent_purge": "not_run"
}
```

不得把本结论写成：

- “上下文裁剪已通过”；
- “派生任务已创建成功”；
- “敏感信息已从 Codex 历史删除”；
- “原任务已安装人工裁剪后的活动上下文”；
- “请求返回 `{}` 即代表持久化成功”。

## 4. 立即停止的执行路径

在新的官方能力通过精确画像和真实 round-trip 验证前，以下行为停止推进：

1. 以 `thread/inject_items` 返回成功作为派生投影成功条件；
2. 创建目标任务后盲目重试注入；
3. 将空目标任务写入正常派生 provenance；
4. 通过直接修改 Codex JSONL、SQLite、认证文件或内部状态来补偿上游缺口；
5. 把原生自动压缩、压缩提示词或“权威上下文补充”描述为确定性删除或硬脱敏；
6. 为了完成 2.4 而引入未经人工批准的协议画像、版本范围或环境变量绕过。

失败后遗留的空目标只进入异常核对范围。CSM 不自动删除它，不自动再次写入，也不把它作为成功派生任务展示。

## 5. 保留并继续完善的能力

以下能力仍是有效交付物，并应继续维护：

- 读取并规范化任务时间线；
- `Keep / Exclude / Summary / Protect` 审查；
- 后续增加 `Replace / Redact`；
- 确定性计算模型可见投影；
- 计划 ID、计划 SHA-256 和 projection SHA-256；
- 内容、能力和任务状态漂移验证；
- 工具调用与结果、文件修改与验证的原子分组保护；
- PendingPlan、失效、取消和审计；
- GUI、CLI、Skill、Hook 和 MCP 对同一计划层的复用；
- 源任务不变和失败后 reconcile 证据。

现阶段用户界面和文档应把该能力称为：

> **上下文审查与投影计划**

而不是把尚未验证的执行层称为“已完成的上下文裁剪”。

## 6. v1.1 验收继续顺序

2.4 关闭后，不恢复当前上下文执行器。v1.1 按以下顺序继续：

1. 完成其余只读、备份、归档、恢复、导入、标题、记忆、Pending、MCP、Skill、Hook、安装和 bundle 验收；
2. **SUPERSEDED（2026-09-01）**：不再继续执行 2.5 人工永久删除应用；2.5 已由独立收口记录按 `CLOSED_WITH_UPSTREAM_BLOCKER` 关闭，原有可信归档、archive-bound 当前备份、单根计划和进程复核条件保留为重新开放门禁；
3. 汇总脱敏证据，明确哪些是真实 App Server 写入，哪些是计划、fixture、offscreen 或上游阻塞；
4. v1.1 可保持内部首次交付候选，但公开说明不得宣称完整上下文裁剪执行可用；
5. 在其余 v1.1 验收正式关闭前，不启动会改变整体安全边界的二期执行能力开发。

## 7. 后续研发优先级

其余 v1.1 验收完成后，研发优先级调整为：

### 第一优先：敏感信息修改

先实现安全、确定性的敏感信息审查与修改能力，重点包括：

- `Replace / Redact / Protect` 计划动作；
- 敏感字段定位、局部替换、统一 diff 和风险提示；
- 内容 SHA-256、原子分组、并发漂移和不可变计划；
- 区分“物理删除”“确定性投影修改”“语义纠正”三种不同保证；
- 先支持 CSM 自有数据和明确可验证的输出；
- 对 Codex 原任务的应用仍保持 capability-gated，不能因计划层完成而宣称已经修改 Codex 历史。

### 第二优先：研究其它上下文应用方向

在敏感信息修改计划层稳定后，再依次研究：

1. 新版本 App Server 是否增加同任务 replacement-history 或自定义 compaction 接口；
2. `thread/inject_items` 在新的精确版本、不同线程创建方式和最小合法 item 组合下是否可持久化并重启后读取；
3. Codex Desktop 本机个人插件的 app-only surface 是否获得可验证的上下文执行能力；
4. 可靠派生任务、原任务活动上下文替换、受控分叉和 provenance 的其它官方路径；
5. 若没有官方、可重读、可恢复的接口，继续保持执行器关闭。

详细实施顺序见：

- [`CodexSessionManager-v1.1-context-projection-and-sensitive-data-plan.md`](../CodexSessionManager-v1.1-context-projection-and-sensitive-data-plan.md)
- [ADR 0009：延期上下文投影应用](../adr/0009-defer-context-projection-application.md)

## 8. 重新开放执行层的硬门禁

只有全部满足以下条件，才能重新开放上下文应用执行层：

- 使用官方 App Server 或正式受支持的本机 app-only 接口；
- 精确 Codex 版本和 schema 画像已人工批准；
- 写入后 `thread/read` 与独立列表接口都能读到预期投影；
- App Server 和 Codex Desktop 重启后仍能读取；
- 后续模型请求实际使用了预期模型可见上下文；
- 超时、断线和响应丢失能通过 reconcile 判定，不依赖盲目重试；
- 原任务或派生目标具有可恢复证据；
- 失败不会破坏源任务；
- 自动化测试、真实 macOS 验收和文档说明一致。

任何一项不满足，执行能力保持关闭。

## 9. 收口结论

2.4 已经到达当前官方能力允许的安全边界。它证明了 CSM 能够：

- 生成并验证上下文投影计划；
- 在上游行为与协议说明不一致时拒绝误报成功；
- 保存源任务；
- 记录失败和遗留目标；
- 将不确定结果降级为上游阻塞。

因此，2.4 在本基线上正式关闭，后续工作不再以“修到 `thread/inject_items` 看似可用”为目标，而以可验证、可恢复和不夸大保证为准。
