## 1. 结论

阶段 2.5 没有通过真实本机永久删除验收。当前能力边界为：

- 永久删除资格盘点、不可变计划和人工审查：可用；
- GUI/CLI 永久删除应用：不可用，失败关闭；
- 本轮唯一一次真实 `thread/delete`：发生部分提交，不能记为通过；
- 当前残留 descendant：保持原状，不盲目重试；
- 重新开放条件：批准与当前数据迁移匹配的 App Server 画像，并在隔离数据根完成单根加 descendant 的完整 round-trip。

这不是 CSM 删除门禁不足，也不是备份、可信归档或确认短语失败。真实写入证明，已批准的 Codex App Server `0.142.1` 与本机由较新 Codex 迁移后的状态存储不兼容，而且官方删除闭包没有覆盖 CSM 从 `thread/read` 恢复出的 descendant。

## 3. 根因

官方 `rust-v0.142.1` 源码同时具备以下行为：

1. 状态迁移只到 `0039`，`delete_threads_strict` 仍查询 `agent_jobs` 和 `agent_job_items`；
2. runtime migrator 允许旧二进制打开迁移版本更高的数据库；
3. `thread/delete` 先删除 rollout/thread store，再清理 App Server 状态库；
4. 状态库清理失败不会恢复已删除的 rollout。

较新官方源码包含 `0042_drop_agent_jobs.sql`，会删除上述两张表；当前主线删除实现也已不再查询它们。本机 bundled Codex 的静态字符串确认包含同一删除迁移。因此，本轮错误与“较新 Codex 已迁移状态库、旧版 0.142.1 随后执行删除”的版本倒挂一致。此处是基于官方源码、二进制版本、错误文本和写后回读得到的推断；为遵守项目边界，没有直接查询 SQLite 迁移表。

此外，写前 CSM 通过完整 `thread/read` 恢复出一个 descendant，但 0.142.1 的 `thread/delete` 没有删除它。结合此前 `thread/list` 状态摘要缺失 parent、`thread/read` 才返回 parent 的真实证据，可判定官方删除子树所依赖的状态映射不完整。即使修复表迁移兼容性，也必须重新证明 descendant 闭包 round-trip，不能只证明根 ID 消失。

## 4. CSM 收口措施

- 默认关闭 `purge apply`，共享执行器在任何 App Server、盘点或写调用之前返回 `CLOSED_WITH_UPSTREAM_BLOCKER`；计划与审查保留。
- GUI 永久删除按钮保持禁用并显示上游阻塞说明，不再打开耗时的计划和确认弹窗。
- 任一对话管理写操作报错后自动刷新任务列表，避免用户再次操作已经变化的陈旧根。
- JSON-RPC 写方法返回错误也按“可能已提交”处理：只回读后置条件，不自动重试；后置条件未满足时同时保留 App Server 原始错误。
- 当前残留 descendant 不作为恢复实验目标，不自动删除、不伪造父子关系、不直接修补 Codex 存储。

## 5. 重新开放门禁

只有同时满足以下条件，才能删除代码中的执行阻断：

1. 选择与当前 Codex 数据迁移匹配的官方 App Server 二进制；
2. 完成新版本、二进制 SHA-256 和 schema SHA-256 的人工批准画像；
3. 在临时隔离数据根构造至少一个根和一个 descendant；
4. 验证计划、备份、可信归档、进程、loaded、后台终端和确认短语门禁；
5. `thread/delete` 返回后确认根和全部 descendants 均不可读取；
6. App Server 重启和 Codex Desktop 重启后再次确认均不可见；
7. 覆盖成功、超时、JSON-RPC 错误和中途状态清理失败，不发生自动重试；
8. 再由用户明确批准一次新的真实账号单根验收。

任何“方法存在”“根 ID 消失”或 fixture/offscreen 结果都不能单独重新开放永久删除。
