# Codex App Server 版本无关操作契约设计

- 状态：待书面复核
- 日期：2026-09-01
- 范围：CodexSessionManager v1.1 的任务读取、完整备份、批量归档和反归档

## 背景

CSM 当前以 `codex_version + 全量 schema_sha256` 精确命中人工画像作为通用写门禁。全量哈希覆盖 App Server 生成的稳定和实验 schema，因此模型、插件或其它无关接口发生变化，也会关闭归档能力。Codex Desktop 更新频繁时，这会迫使 CSM 为未影响任务管理语义的版本重复发布画像。

CSM 的发布周期必须与 Codex Desktop 的版本周期解耦。Codex 版本、二进制哈希和全量 schema 哈希继续作为诊断与审计证据，但不再直接决定归档或反归档是否可用。

## 决策

CSM 改为按操作评估经过人工定义的最小协议契约：启动时从实际 Codex 二进制生成 schema，判断当前运行时是否向后兼容 CSM 已审核的读取、备份、归档和反归档契约。兼容判断与 Codex 版本号无关，也不要求全量 schema 相等。

契约规则由 CSM 代码库人工维护；只有相关语义发生变化时才发布新的规则版本。运行时只能判断实际协议是否满足已有规则，不能自动学习、扩展或批准新的写入语义。相关契约发生不兼容变化时，只关闭受影响的操作，其余读取和兼容操作继续可用。

App Server 仍是 Codex 任务在线读取和写入的唯一边界。CSM 不直接修改 JSONL、SQLite、认证文件或 Codex 配置。

## 目标

- Codex Desktop 常规升级不要求同步更新或重新发布 CSM。
- 版本号变化、二进制哈希变化和无关 schema 变化不关闭归档能力。
- 写能力由操作和目标任务共同决定，不再由单个全局 `write_enabled` 表示。
- 普通历史与分页历史独立评估；分页能力变化不阻塞普通历史任务。
- 不兼容变化必须给出具体操作、方法和字段原因，而不是笼统提示“版本不可信”。
- 保留不可变计划、能力指纹、目标状态与内容指纹、完整后代闭包、备份复验、写后重读和超时 reconcile。

## 非目标

- 不承诺在 OpenAI 删除、改名或改变归档接口语义后仍自动写入。
- 不恢复永久删除能力。
- 不开放上下文应用、原任务修改或派生投影执行。
- 不把 Codex Desktop 安装路径、版本号或签名来源单独视为写权限。
- 不构建任意 App Server 方法的通用动态调用器。

## 领域模型

### 运行时协议证据

每次探测继续记录：

- Codex 可执行文件路径、版本、平台签名信息和 SHA-256；
- 稳定与实验 schema 的全量 SHA-256；
- 初始化响应指纹；
- 稳定与实验方法集合。

这些字段用于诊断、计划失效和审计追踪，不用于按版本授权。

### 操作契约

一个操作契约包含：

- 稳定的 `contract_id` 和契约规则版本；
- 所需方法及其最低稳定性要求；
- CSM 实际发送的请求字段、类型和必需性；
- CSM 实际读取的响应、通知和任务字段；
- 允许的向后兼容变化；
- 需要立即失败关闭的变化；
- 写前条件和写后可观测状态。

契约规则规范化后计算 `contract_rule_fingerprint`。实际 schema 中与该规则相关的投影规范化后计算 `runtime_contract_fingerprint`。计划同时绑定规则指纹、运行时契约指纹和全量 schema 哈希；执行前任一值变化都必须重新规划。

### 操作能力

能力矩阵提供按操作查询，而不是单一全局布尔值：

```text
inventory.common
history.legacy
history.paginated
archive
unarchive
```

每项结果包含 `available`、`contract_id`、规则与运行时指纹、稳定性和结构化阻塞原因。GUI、CLI、Skill 和领域工作流必须调用同一查询边界。

## 最小契约

| 契约 | 必要 App Server 能力 | 关键语义 |
|---|---|---|
| `inventory.common.v1` | `initialize`、`thread/list`、`thread/read`、`thread/loaded/list` | ID、归档状态、运行状态、父子关系、临时状态和历史模式可确定 |
| `history.legacy.v1` | `thread/read` | 返回的 turns/items 能完整建立内容指纹和逻辑备份 |
| `history.paginated.v1` | `thread/turns/list` | `itemsView=full`、升序分页、cursor 终止和完整 items 可验证 |
| `archive.v1` | `thread/archive`、归档通知、归档后列表/读取 | 请求精确指向一个根；执行后完整闭包逐项重读为已归档 |
| `unarchive.v1` | 已归档列表/读取、`thread/unarchive`、恢复通知 | 请求精确指向一个根；执行后目标闭包逐项重读为活跃 |

`history.paginated.v1` 可以依赖显式协商的实验方法，但该依赖只影响分页任务。普通历史任务只需要 `history.legacy.v1`。

## 兼容性规则

以下变化自动视为兼容，不要求发布新的 CSM：

- Codex 版本、二进制哈希或全量 schema 哈希变化；
- 增加与上述契约无关的方法、定义或 schema 文件；
- 无关方法在稳定与实验集合之间迁移；
- 描述、标题、默认值、定义顺序或 JSON 对象键顺序变化；
- 契约对象增加非必需字段，且该字段不改变 CSM 使用的字段类型、必需性或已知枚举语义；
- 契约响应增加联合类型分支，但当前目标实际返回值仍属于 CSM 已理解的分支；
- CSM 依赖的实验方法提升为稳定方法。

以下变化只阻塞受影响的操作：

- 必要方法被删除、改名或从稳定降为必须显式启用的实验方法；
- CSM 请求字段被删除、改名、改为不兼容类型或增加 CSM 无法满足的必填字段；
- CSM 使用的响应字段被删除、改为不兼容类型或改变必需性；
- 当前任务返回未知的关键枚举值、历史模式、状态或关系类型；
- 分页不再提供可证明终止的 cursor，或无法请求完整 items；
- 归档/反归档成功响应和写后可观测状态无法建立一致映射；
- schema 生成、解析或契约投影失败。

兼容比较是静态规则判断，不会把未知字段或一次成功响应写回信任列表。真正改变相关语义的新契约仍需人工审查和新的契约规则版本。

## 运行流程

1. 运行时解析器优先选择 Codex Desktop 内置二进制，并记录 macOS 代码签名或 Windows Authenticode 结果。来源信息只用于诊断和防止误选二进制。
2. 从该二进制生成稳定与实验 schema，并保存内存中的规范化证据；临时原始 schema 在探测结束后删除。
3. 契约评估器分别计算五项操作能力。一个契约失败不得把整个 App Server 标记为只读。
4. 库存工作流根据每个任务的 `historyMode`、状态、关系和内容完整性计算任务级资格。
5. GUI 或 CLI 选择多个任务时，只有所有目标都支持同一动作且不存在混合归档状态时才启用归档/反归档。
6. 备份成功并完整复验后，生成绑定目标闭包、任务指纹、契约指纹、运行时证据和有效期的不可变计划。
7. 执行前重新探测契约并重新读取目标；能力或目标变化时计划过期，不自动重试。
8. 只调用官方 `thread/archive` 或 `thread/unarchive`。
9. 无论请求返回成功、超时还是连接中断，都逐项重读计划中的完整闭包；以实际状态判断完成、未完成或不确定。
10. 审计记录只保存脱敏标识、指纹、证据层级和结果，不保存任务正文。

## GUI、CLI 与 Skill 行为

- GUI 不再显示“当前 Codex 版本未在精确画像中”作为归档禁用原因。
- 操作禁用信息必须指向具体契约，例如“分页历史缺少完整 items 能力”或“归档响应契约不兼容”。
- 普通历史任务可归档时，分页历史契约失败不能禁用普通历史任务。
- CLI doctor 和 schema audit 输出保留版本、二进制和全量 schema 哈希，同时增加逐项契约结果。
- Skill 只能调用与 GUI/CLI 相同的工作流边界，不能通过 MCP 参数或提示词绕过契约资格。
- MCP 保持读取、审查和计划能力，不新增归档执行工具。

## 失败与恢复

- 无法确认契约兼容时，对该操作失败关闭，但读取、备份和计划保持可用。
- 未知关键任务值只阻塞包含该任务的选择，不扩大到其它已知任务。
- App Server 写入超时后禁止盲目重试；必须先重读并 reconcile。
- 部分闭包归档或恢复视为不完整结果，保留原计划和备份证据，并给出逐项状态。
- 全量 schema 变化本身只产生诊断事件，不产生错误或要求用户降级。

## 迁移

- `codex_version`、二进制哈希和全量 `schema_sha256` 保留在能力矩阵和审计模型中，但从授权条件中移除。
- 精确版本画像不再作为运行时写白名单；现有画像保留为兼容比较和回归测试语料，不再按 Codex 版本持续追加。
- schema audit 从“是否命中精确版本画像”改为“每个操作契约是否兼容”，并保留完整差异报告。
- 新增 ADR 取代 ADR 0001 中“精确版本 + 全量 schema 哈希授权”的部分；ADR 0001 的 App Server 唯一写入边界继续有效，并补充 `SUPERSEDED IN PART` 标记。
- README、AGENTS、CONTEXT、Skill、安全参考、验收手册和发布说明同步使用“版本无关、契约敏感”的表述。
- 历史验收报告不重写；需要说明现行边界时只增加 `SUPERSEDED` 标记或由新文档引用。

## 测试策略

### 单元测试

- 版本号和全量 schema 哈希变化、相关契约不变：归档仍可用。
- 增加无关方法或可选字段：归档仍可用。
- 删除 `thread/archive` 或改变 `threadId` 类型：只禁用归档。
- `thread/turns/list` 不兼容：只禁用分页任务，普通历史任务仍可归档。
- 当前任务出现未知关键状态或历史模式：只阻塞该任务。
- 契约或目标指纹在计划后变化：执行拒绝并要求重新规划。

### 集成测试

- 假 App Server 提供多个不同版本号和无关 schema 差异，共用同一归档契约。
- 假 App Server 模拟分页缺失、部分后代归档、超时后已完成和超时后未完成。
- GUI、CLI 和 Skill 对同一目标得出相同资格和阻塞原因。
- 所有写入测试使用隔离数据根；不得复制真实 Codex 数据作为 fixture。

### 本机验收

- 使用当前 Codex Desktop 内置二进制，证明不依赖预置版本画像即可得到逐项契约结果。
- 在用户明确指定、已完整备份的测试任务上分别完成一次归档和反归档，并逐项重读闭包。
- 记录真实 App Server、真实账号、真实用户选择与自动化测试证据的层级差异。
- 不执行永久删除、上下文应用或直接数据文件修改。

## 验收标准

- 代码中不存在以 `codex_version + 全量 schema_sha256` 命中作为归档/反归档授权条件。
- 将 Codex 版本替换为任意新值、增加无关 schema 内容后，契约兼容的归档测试仍通过。
- 相关契约发生不兼容变化时，只有受影响操作失败关闭且原因可读。
- 不完整内容、后代闭包、备份或计划仍能独立阻止写入。
- `scripts/check.sh`、源码工作流、Skill 工作流和 fresh macOS bundle 验收通过。
- 本机真实账号归档/反归档结果必须有写后重读证据，不能由 fixture、offscreen GUI 或假 App Server 替代。

## 取舍

该设计不能消除真正的上游破坏性变化，但把维护触发条件从“Codex 发布了新版本”缩小为“CSM 实际使用的协议契约发生不兼容变化”。这是在高频更新环境下保持长期兼容，同时不以猜测执行账号写入的最小边界。
